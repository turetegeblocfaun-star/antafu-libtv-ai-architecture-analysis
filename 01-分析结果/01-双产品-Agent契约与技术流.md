# 双产品 Agent 契约与技术流判定

## 1. 分类标准

| 类型 | 判断条件 | 本报告处理方式 |
|---|---|---|
| 固定工作流 | 步骤、分支和工具预先确定，用户输入不改变规划 | 只有可见固定步骤时使用 |
| 单 Agent | 一个持续身份读取上下文、做功能判断并选择工具/下一步 | 可由多个模式、工具和模型支撑 |
| 多 Agent | 至少两个可辨识 Agent，存在触发、交接、重入或结果消费关系 | 必须有名称/职能和交接证据 |
| Agent + 工作流 | Agent 负责理解与路由，工作流负责稳定执行具体任务 | 两款产品当前最符合的分类 |

“有四个入口”“有十个模型”“有一百个 Skill”不等于多 Agent。模型是能力执行器，Skill 更接近任务模板/工作流；除非页面出现独立身份和交接关系，否则不计为 Agent。

## 2. 总体判定

| 产品 | 是否使用 Agent | 单/多 Agent | 工作流关系 | 置信度 | 结论 |
|---|---|---|---|---|---|
| 蚂蚁阿福 | 【合理推断】是 | 【合理推断】单一可见 Agent；内部形态【未知】 | 四类任务入口和深度/极速模式驱动不同工具工作流 | 中高 | 单 Agent 主控的 Agent-in-Workflow |
| LibTV | 【已确认】页面明确写“LibTV Agent” | 【合理推断】单一可见 Agent；内部形态【未知】 | Skill 展开多阶段创作，手动/自动控制工作流，模型承担执行 | 高 | 单 Agent 主控的 Skill/Workflow Orchestration |

## 3. 蚂蚁阿福技术流

### 3.1 可见主链

```text
用户选择任务入口与回答模式
  -> 输入文本或上传图片/PDF
  -> 阿福会话身份接收当前输入和历史上下文
  -> 按显式入口路由到健康问答 / 深度搜索 / 报告解读 / 药盒识别
  -> 调用相应功能工具（搜索、引用整理、PDF解析、图像理解/OCR）
  -> 生成结构化回答、来源、免责声明和追问
  -> 写入会话历史、任务状态和反馈入口
```

### 3.2 为什么不是纯工作流

- 【已确认】支持开放式健康问题和多轮追问，不是固定表单。
- 【已确认】用户补充“怀孕8周”后，回答重新比较前后版本并改变建议。
- 【已确认】深度搜索会检索、汇总并生成带来源答案。
- 【合理推断】需要理解上下文、判断用户意图和组织不同输出，符合 Agent 特征。

### 3.3 为什么不能判定多 Agent

- 【已确认】用户可见身份始终是“我是阿福，你的AI医生朋友”。
- 【已确认】没有出现第二个具名 Agent、角色接管提示或 Agent 间交接卡。
- 【已确认】“深度思考/极速模式”是回答模式，“健康问答/报告解读”等是任务入口。
- 【未知】后台是否用多个模型进程、审校器或专业子 Agent；页面无法证明。

### 3.4 单 Agent I/O 契约

| 项目 | 契约 |
|---|---|
| 核心目标 | 提供健康科普、文献检索、报告说明和药盒信息识别，并保持医疗安全边界 |
| 触发 | 用户发送文本、上传单一允许类型文件、追问、补充条件、重新生成或停止 |
| 输入 | 当前问题、任务入口、深度/极速模式、图片/PDF、会话历史、工具结果 |
| 判断 | 任务类型、输入是否合法、是否需检索、是否存在红旗症状、旧建议是否被新条件推翻 |
| 工具 | `<专业资料搜索工具>`、`<PDF解析工具>`、`<图像理解/OCR工具>`、`<会话读写工具>`；均为功能命名 |
| 输出 | 结构化健康说明、来源/引用、报告异常项、药盒文字、免责声明、追问、任务状态 |
| 停止 | 用户中断、混合上传、输入不可读、紧急风险需就医、工具失败或证据不足 |
| 完成 | 回答实际存在、来源与声明可见、任务不再生成、状态写入历史；高风险结论需保守表达 |

### 3.5 工作流分支

| 分支 | 输入 | 关键工具 | 主要状态 | 已观察问题 |
|---|---|---|---|---|
| 健康问答 | 文本 + 历史 | 资料检索/生成 | generating → completed | 新条件出现后旧建议未显式失效 |
| 深度搜索 | 研究问题 + 深度模式 | 搜索、来源整理 | searching → thinking → completed/interrupted | 中断后“已停止”与“正在调用工具”冲突 |
| PDF报告 | 单一 PDF | PDF解析、生成 | uploaded → parsing → completed | PDF不能附加文字要求；表述可能过度确定 |
| 图片报告 | 图片 + 可选约束 | 视觉/OCR、生成 | uploaded → analyzing → completed | 与 PDF 能力不一致 |
| 药盒识别 | 图片 + 可选要求 | 视觉/OCR | analyzing → completed | 历史标题被泛化为“图片解读” |

## 4. LibTV 技术流

### 4.1 可见主链

```text
用户选择空白画布 / Skill / 模型 / 自动或手动模式
  -> 输入创意和附件
  -> LibTV Agent 读取当前请求、Skill约束、项目与余额
  -> Skill 将任务展开为阶段化创作步骤
  -> 手动模式逐次确认，自动模式连续执行
  -> 路由到图片模型、视频模型或画布/项目功能
  -> 生成并写入项目资产
  -> 页面展示任务、预览、编辑和最终视频（本次未验证）
```

### 4.2 为什么不是纯工作流

- 【已确认】页面明确存在“LibTV Agent”和自由文本创意输入。
- 【已确认】用户可以从 Skill 开始，也可以不选 Skill；可以切换模型和自动化程度。
- 【已确认】Skill 对输入和输出做语义约束，例如品牌、主角、比例和时长。
- 【合理推断】Agent 负责把开放式需求映射到 Skill 阶段、模型和项目动作。

### 4.3 为什么不能判定多 Agent

- 【已确认】可见身份只有“LibTV Agent”。
- 【已确认】Skill 卡片展示的是流程和能力，没有独立 Agent 加入/离开或交接记录。
- 【已确认】Seedance、Minimax、Kling 等是模型选择，不是 Agent 身份。
- 【未知】剧本、角色、分镜、视频等阶段是否由后台子 Agent 分工；本次未进入画布，无法观察。

### 4.4 单 Agent I/O 契约

| 项目 | 契约 |
|---|---|
| 核心目标 | 将创意、Skill、参考素材和模型偏好转为可追踪的项目任务与视频资产 |
| 触发 | 发送创意、添加 Skill、选择模型、切换手动/自动、打开/修改项目 |
| 输入 | 当前需求、附件、Skill、模型、生成模式、项目、余额、已有资产和工具结果 |
| 判断 | 输入是否满足 Skill、是否需要确认、余额是否足够、用何模型、局部还是全量重做 |
| 工具 | `<项目创建/读取工具>`、`<图片生成工具>`、`<视频生成工具>`、`<资产写入工具>`、`<余额检查工具>`；均为功能命名 |
| 输出 | 计划/确认、项目、图片/视频资产、预览入口、状态、成本信息和恢复动作 |
| 停止 | 用户中断、余额不足、安全拦截、输入缺失、工具失败、状态写入失败 |
| 完成 | 资产实际存在、项目状态写入成功、结果验证通过、用户确认记录完整 |

### 4.5 Skill 工作流分支

| 分支 | 触发 | 典型阶段 | 控制方式 | 本次证据 |
|---|---|---|---|---|
| 空白创作 | 新建画布 | 用户自行编排 | 画布交互 | 入口可见，未进入画布 |
| Skill创作 | 添加 Skill | 以皮克斯动画广告为例：角色立绘→分镜草图→广告歌词→视频→Logo | 手动/自动 | Skill 详情可见，执行未验证 |
| 直接模型 | 选择图片/视频模型 | 单次生成或编辑 | 模型参数 | 模型列表可见，执行未验证 |
| 案例复用 | 查看创作过程 | 参考公开作品流程 | 【未知】 | 按钮存在，部分点击无反馈 |

## 5. 两款产品的数据与控制差异

| 维度 | 蚂蚁阿福 | LibTV |
|---|---|---|
| 任务中心 | Conversation/Answer | Project/Task/Asset |
| Agent 控制 | 用户先选任务入口，Agent在路径内回答 | 用户选 Skill/模型/模式，Agent编排多阶段创作 |
| 主要工具 | 搜索、引用、PDF解析、图像理解/OCR | 图片/视频模型、项目/资产、预览/剪辑、余额 |
| 核心上下文 | 症状、限制条件、报告、来源、历史回答 | 创意、Skill、模型、项目、资产引用、余额 |
| 主要风险 | 医疗过度确定、旧建议残留、来源不一致 | 无回执、重复项目、任务/资产状态不一致、重复扣费 |
| 推荐完成门 | 回答+来源+安全边界+历史状态 | 资产+项目状态+验证+用户确认+成本记录 |

## 6. 多 Agent 的建议形态（不是现状结论）

### 蚂蚁阿福 To-Be

【建议设计】采用 **Supervisor + Specialist + Independent Reviewer**：

- 健康主控 Agent 负责意图、上下文和用户沟通。
- 检索、报告解析、药盒视觉作为专业 Worker。
- 医疗安全审校 Agent 独立检查高风险表述、来源一致性和旧建议失效。
- 审校不通过时返回主控修改，不直接向用户输出第二套冲突答案。

### LibTV To-Be

【建议设计】采用 **Supervisor + DAG Workers + Asset Validator**：

- 创作主控 Agent 管理项目目标、确认门、成本和交接。
- 剧本/角色/场景/分镜/媒体生成可作为按需 Worker，但以版本化资产 DAG 交接。
- 独立资产验证器检查实际文件、引用、时长、一致性和页面状态。
- Worker 不是固定全部调用；只在 Skill 阶段和依赖满足时启动。
